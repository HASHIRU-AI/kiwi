# Kiwi Benchmarking Library (`kiwi_bench`)

A focused library for evaluating the generation quality of distributed LLM inference systems compared to a single-GPU baseline. Since distributed systems often implement optimization techniques like quantization (INT8) and sparsity (CSR), output quality can diverge from standard fp16/bf16 inference. This tool measures that divergence.

## Rated Metrics and How They Work

This tool focuses on quality (performative output) rather than speed. It includes three primary evaluators:

### 1. Exact Match Evaluator (`ExactMatchEvaluator`)
**What it rates:** Deterministic output stability.
**How it works:** It checks if the text generated by the distributed system is an exact string match to the single-GPU baseline.
**When to use:** Use this when no quantization/sparsity is enabled, or when you are testing whether your distributed system produces bit-for-bit identical results to a local `transformers` pipeline. If it doesn't match exactly, the length differences are reported.

### 2. Semantic Similarity Evaluator (`SemanticSimilarityEvaluator`)
**What it rates:** Meaning preservation despite output divergence.
**How it works:** It uses a `sentence-transformer` embedding model (default: `all-MiniLM-L6-v2`) to convert both the baseline response and the distributed response into dense vectors. It then computes the **Cosine Similarity** between these vectors. 
**When to use:** Use this when testing INT8 quantization or CSR sparsity. The exact strings will likely diverge, but a high semantic similarity (e.g., >0.95) indicates the model still understands the prompt and generates a conceptually identical answer.

### 3. LLM-as-a-Judge Evaluator (`LLMJudgeEvaluator`)
**What it rates:** Subjective helpfulness, accuracy, and overall quality.
**How it works:** It uses a strong external LLM (e.g., GPT-4 via OpenAI API) to grade the test response. The judge LLM is provided the original prompt, the baseline response, and the test response. It returns a score from 1 to 10 evaluating how well the test response compares to the baseline, along with reasoning.
**When to use:** Use this for complex, open-ended conversational evaluations (similar to MT-Bench or AlpacaEval). This catches edge cases where the semantic similarity might be high but the actual generated facts are slightly corrupted or hallucinatory due to severe quantization.

### 4. Performance Evaluator (`PerformanceEvaluator`)
**What it rates:** Throughput (tokens/sec) and overall generation speedup.
**How it works:** Tracks the time spent processing the generation request on both the baseline and test systems, then calculates `tokens_generated / latency`. It also outputs a `speedup_x` multiplier. 
**When to use:** Use this combined with quality metrics to answer "Does the `USE_INT8` and `USE_CSR` bandwidth saving actually translate to a higher token throughput, and at what cost to quality?"

## Usage

You can use the library programmatically or via the CLI.

### CLI Usage

```bash
python -m benchmarks.cli \
    --model "meta-llama/Llama-2-7b-chat-hf" \
    --dataset "dummy" \
    --limit 3 \
    --use-transformers-baseline \
    --test-url "http://localhost:8080" \
    --evaluators "exact_match,semantic" \
    --output "results.json"
```

### Programmatic Usage

```python
from benchmarks import TransformersRunner, OpenAIRunner, SemanticSimilarityEvaluator

# Setup runners
baseline = TransformersRunner(dtype="bfloat16")
kiwi_system = OpenAIRunner(base_url="http://localhost:8080")

# Setup Evaluator
evaluator = SemanticSimilarityEvaluator()

# Run
prompt = "Explain quantum computing."
base_resp = baseline.generate("my-model", [{"role": "user", "content": prompt}])
test_resp = kiwi_system.generate("my-model", [{"role": "user", "content": prompt}])

metrics = evaluator.evaluate(prompt, base_resp, test_resp)
print("Semantic Similarity:", metrics["semantic_similarity"])
```

## Automated Orchestration

To systematically test the Kiwi distributed inference concept across various layouts, you can use the built-in orchestrator. It acts as both a CLI tool and a library, dynamically generating docker-compose files and applying network latency rules to test the robustness and speedup of optimizations like INT8 and CSR.

### YAML Configuration
Create a `scenarios.yaml` file to define your test matrix:
```yaml
scenarios:
  - name: "2-node-baseline"
    model: "Qwen/Qwen2.5-0.5B-Instruct"
    use_int8: false
    use_csr: false
    workers: [1.0, 1.0]

  - name: "2-node-optimized-high-latency"
    model: "Qwen/Qwen2.5-0.5B-Instruct"
    use_int8: true
    use_csr: true
    csr_sparsity: 0.4
    network:
      latency_ms: 100
      bandwidth_mbit: 100
    workers: [1.0, 1.0]
```

### Running the Orchestrator
```bash
python -m benchmarks.orchestrator --config benchmarks/scenarios.yaml --limit 3
```
This will automatically spin up each cluster configuration, run the benchmarks, teardown, and dump the JSON metrics for each scenario in the `benchmark_results` directory.

### Using as a Library
```python
from benchmarks import load_scenarios, run_orchestration

scenarios = load_scenarios("my_custom_scenarios.yaml")
run_orchestration(scenarios, dataset="dummy", limit=5, output_dir="my_results")
```

## Adding New Datasets
The `datasets.py` module supports a `HuggingFaceDatasetLoader` which can pull standard instruction datasets (like `tatsu-lab/alpaca`) directly from the Hugging Face Hub for automated testing.
